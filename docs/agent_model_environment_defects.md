# 模型可用环境下的在线 Agent 功能缺陷分析

更新时间：2026-08-17

## 1. 文档目的

本文评估 CoursePilot 在线 Agent 在“默认结构化模型稳定可用”的前提下，是否能够准确理解用户意图并完成用户任务。

本文只讨论以下六项在线能力：

1. 对话与意图路由；
2. 学习画像；
3. CSDIY 课程导航；
4. 已审核 StudyKit 学习；
5. 练习选择与答案反馈；
6. 多语言静态代码辅导。

本文不建议放宽现有安全和数据边界。以下架构约束继续成立：

- 普通聊天不能触发离线 StudyKit authoring；
- 在线课程事实只能来自通过门禁的 `StudyKitStore` 或未来经过权限过滤的检索；
- 练习答案、分数、正确率和掌握度不持久化；
- 代码辅导保持静态分析，`ran_code=false`；
- 模型不能创造课程、版本、讲次、引用或权限事实；
- 学习者输出不能泄漏 `expected_evidence`、evaluation、rubric 或审计字段。

## 2. 总体结论

在模型可用的环境中，当前系统更接近“规则驱动的能力路由器，附带若干受限模型调用”，还不是能够稳定执行多步骤学习任务的任务型 Agent。

主要结构性问题是：

1. 模型通常只负责分类或生成一段结构化文本；
2. 普通自然语言请求仍可能被关键词规则提前截断；
3. 模型缺少完整对话和明确的任务状态；
4. 系统只支持单一主意图，不能显式拆解和执行多步骤请求；
5. 课程导航、概念解释和练习选择等能力没有充分使用模型进行受控语义理解；
6. 检索、引用和上下文绑定能力不足，限制了模型完成任务的准确性。

问题严重度如下：

| 功能 | 严重度 | 核心问题 |
| --- | --- | --- |
| 对话与意图路由 | 高 | 规则优先截断模型，只支持单意图，模型缺少完整对话 |
| 学习画像 | 中高 | 原文引用不能证明语义正确，候选确认和纠错粒度不足 |
| 课程导航 | 高 | 推荐仍依赖关键词和固定加权，无法理解复杂学习需求 |
| StudyKit 学习 | 高 | 词法检索限制模型证据，概念解释缺少受控模型组织 |
| 练习与反馈 | 高 | 出题不自适应，练习和答案上下文绑定脆弱，反馈单轮化 |
| 静态代码辅导 | 中高 | 静态事实不足，诊断循环、代码版本和证据绑定不完整 |

## 3. 对话与意图路由

相关实现：

- `app/agent/router.py`
- `app/agent/orchestrator.py`
- `app/agent/contracts.py`

### 3.1 规则可能在模型理解前作出错误判断

当前路由执行顺序是确定性规则优先，只有规则完全未命中时才调用结构化模型。该策略适合 `/help`、删除画像、明确 practice ID 等高精度命令，但不适合作为普通自然语言的主路由。

例如：

- “我学过反向传播，为什么这里还要保存中间激活？”可能被画像信号抢先匹配；
- “为什么这个程序只在 CUDA 上报错？”可能直接进入代码辅导，却没有先判断用户是在问概念、环境差异还是要求分析具体代码；
- “第 10 页为什么这样定义？”会进入材料问答，但系统尚未解析“第 10 页”属于哪个材料。

即使模型可用，这些请求也可能不经过模型意图理解。

### 3.2 路由模型缺少完整对话

结构化分类主要使用最新用户消息和已解析的课程上下文，而不是完整对话语义。它难以稳定理解以下指代：

- “那来一道难一点的”；
- “继续上一题”；
- “换成代码阅读题”；
- “按刚才那个课程解释”；
- “我说的是第二种情况”。

课程身份只能解决部分指代，不能恢复上一轮任务、当前练习、提示层级或用户刚刚选择的候选。

### 3.3 只支持单一意图

`RouteDecision` 只能返回一个 `intent`。例如：

> 我每周有 5 小时，想学操作系统，请记录下来并推荐一门课。

该请求实际包含画像更新和课程推荐两个任务。当前实现只能选择一个主分支；画像观察即使作为副作用发生，也不等于系统显式理解并完成了两个任务。

### 3.4 缺少统一的任务计划和前置条件执行器

路由结果可以返回 `required_context`，但编排层没有统一处理缺失字段、追问、恢复和继续执行。各能力服务分别检查课程、讲次、practice ID、答案或代码，导致追问和任务恢复行为不一致。

### 3.5 课程目录身份和在线学习身份未完全分离

模型给出的课程身份通过 online-ready `StudyKitStore` 验证。一门课程即使真实存在于目录中，只要还没有 ready StudyKit，就可能无法作为模型解析出的课程上下文通过验证。这会影响课程导航意图，而课程导航本应允许展示目录存在但尚未上线的课程。

### 3.6 改进方向

将路由改为：

```text
确定性安全命令
  → 模型基于完整对话理解目标
  → 生成结构化 TaskPlan
  → 逐任务检查身份、权限和缺失字段
  → 顺序执行能力
  → 根据执行结果决定继续、追问或透明降级
```

建议任务计划至少包含：

```json
{
  "user_goal": "string",
  "tasks": [
    {
      "task_id": "string",
      "capability": "enum",
      "arguments": {},
      "required_context": [],
      "depends_on": []
    }
  ],
  "course_references": [],
  "clarification": null
}
```

模型只负责意图、参数和依赖理解；课程事实、权限和执行结果仍由确定性服务验证。

## 4. 学习画像

相关实现：

- `app/profile/service.py`
- `app/profile/repository.py`
- `app/profile/contracts.py`

### 4.1 原文引用不能证明抽取语义正确

当前模型候选若声明为 `confirmed`，只要 `evidence_quote` 是用户原文中的精确子串，就可能保留为 confirmed。

但“引用来自用户”不代表“结构化事实被这段引用支持”。例如：

> 我没学过 Python，只看过一点 C++。

模型可能引用整句话，却错误产生 `background=Python`。当前检查能够验证来源，却不能验证否定、转折和字段值之间的语义蕴含关系。

### 4.2 候选确认粒度过粗

当前“确认记录”会确认用户全部 inferred 候选，而不是确认用户当前指向的单条事实。用户无法自然表达：

- 确认学习方向，但拒绝讲解偏好；
- 把某条候选修改后再确认；
- 只确认最近一条候选。

### 4.3 过期 inferred 候选可能被重新确认

`confirm_inferred()` 更新所有未 superseded 的 inferred 记录，但没有同时限定 `expires_at` 尚未过期。过期记录虽然不会被正常画像查询返回，仍可能在全量确认时被更新为 confirmed 并清除过期时间。

这是需要直接修复的持久化逻辑缺陷。

### 4.4 背景事实缺少程度和时间维度

当前 `background=Python` 无法区分：

- 只读过语法；
- 能独立完成项目；
- 两年前学过但已经遗忘；
- 只熟悉特定库；
- 用户主观认为基础薄弱。

这会降低后续个性化解释和课程推荐的准确性。

### 4.5 当前课程提及判断存在特定课程模式

`_mentions_course()` 主要识别 `6.7960`、Lecture 和“第几讲”。该判断没有充分复用已经通过 Store 验证的通用课程实体，因此扩展到更多课程后可能不能稳定更新 `active_course`。

### 4.6 画像观察可能成为无关副作用

除 Help 和画像管理外，多数能力执行前都会观察最新消息。包含“学过”“基础”“目标”等文字的课程问题可能触发画像模型，即使用户并没有在陈述个人事实。

### 4.7 改进方向

- 为每个画像候选建立独立 candidate/fact ID；
- 只允许按 ID 确认、修改或拒绝候选；
- `confirm_inferred()` 必须检查记录尚未过期；
- 对 confirmed 候选执行引用与结构化事实之间的语义蕴含检查；
- 加强否定、转折、程度和时间表达解析；
- 只观察用户明确的自我陈述；
- 使用通用、已验证的课程实体更新 active course；
- inferred 事实继续只作为待确认候选，不能参与正式建议。

## 5. CSDIY 课程导航

相关实现：

- `app/catalog/courses.py`
- `app/course_navigation/service.py`

### 5.1 复杂学习需求仍被压缩成少量关键词方向

当前主要识别 systems、ml_ai、algorithms、security、web_frontend、web_backend 和 theory。

下面的请求无法仅靠方向词表准确表达：

- “想学能帮助我理解 PyTorch 编译栈的课程”；
- “希望从 C++ 过渡到 GPU 编程”；
- “想做数据库内核，但操作系统基础一般”；
- “三个月后要上研究生分布式系统课程”；
- “每周只有两小时，希望先选负担轻的课程”。

### 5.2 排序不能充分表示课程适配度

当前得分主要来自课程身份、方向关键词、online readiness、Manifest 和离线制作状态。它没有系统使用：

- 先修课；
- 难度和工作量；
- 用户每周时间；
- 编程语言；
- 理论或项目偏好；
- 用户背景与课程要求差距；
- 课程之间的先后依赖。

因此当前能力更接近“课程目录检索”，而不是可靠的个性化课程推荐。

### 5.3 readiness 可能压过用户适配度

online-ready 和 authoring 状态会直接增加排序分数。这有助于优先展示当前可用内容，但可能让“立即可在线学习”的课程排在“更符合用户目标”的课程之前。

应分别表达：

- 最符合用户目标的课程；
- 当前可以立即使用 StudyKit 学习的课程。

### 5.4 推荐理由不足

当前输出课程状态和链接，但没有明确说明课程为何适合用户、使用了哪些已确认的画像事实、存在什么先修缺口。

### 5.5 改进方向

- 让模型把自然语言需求转换为受控查询结构；
- 由可信目录服务执行查询，模型不能创造课程事实；
- 增加先修、难度、工作量、语言和学习成果等经审核字段；
- 将用户适配度和 online readiness 分开排序和展示；
- 输出基于 confirmed 画像和目录字段的推荐理由；
- 将 `CatalogCourseIdentity` 与 `StudyKitCourseIdentity` 分离；
- 支持候选消歧、分页和显式过滤。

## 6. 已审核 StudyKit 学习

相关实现：

- `app/catalog/studykits.py`
- `app/learning/service.py`

### 6.1 词法检索在模型调用前限制了证据

材料问答先通过术语命中和简单 token 重叠，从 StudyKit 的 `core_concepts`、`outline` 和 `common_misconceptions` 中最多选择四条证据，然后才调用模型。

如果用户使用同义表达、隐含关系或跨概念提问，相关证据可能在模型看到问题之前就被排除。模型可用并不能弥补候选证据选择错误。

### 6.2 缺少权限过滤的 SourceChunk 检索

当前在线能力无法稳定完成：

- 总结指定页面；
- 解释图表或公式布局；
- 比较两段原文；
- 查找讲义中的精确定义；
- 核对某个细节是否真的出现；
- 回答 StudyKit 摘要没有覆盖的材料问题。

这是材料任务完成能力的主要缺口。

### 6.3 概念解释没有充分使用模型

概念解释分支选择一个 `core_concept` 后，主要按模板输出定义、直觉、公式、说明、误区和页码。它不能充分响应：

- “用我熟悉的 C++ 类比解释”；
- “先举例，再给公式”；
- “比较两个概念”；
- “只解释其中一个步骤”；
- “判断我下面的理解是否正确”。

### 6.4 引用合法不等于主张得到支持

材料问答会检查模型返回的 citation ID 是否属于允许集合，但没有逐项验证回答中的每个主张是否被对应证据支持。模型可能返回合法引用，却在回答中加入证据没有表达的推论。

### 6.5 archive 生命周期门禁可以进一步收紧

当前 archive 查询重点检查 build/document 的 `review_status=approved`。如果 `build_status` 和 `document_status` 也承载正式生命周期语义，应同时限定允许状态，避免已批准但未完成或非最终状态的记录进入在线 Store。

### 6.6 模型无法主动规划下一步检索或澄清

证据不足时当前通常直接拒绝或降级。一个任务型 Agent 还应能够：

- 询问用户指的是哪个课程、版本或讲次；
- 提示当前可用讲次；
- 请求用户授权或选择资料；
- 改写查询并进行第二轮受控检索；
- 明确说明缺少哪类证据。

### 6.7 改进方向

- 首先实现按 owner/session/material_set/course/version/unit 过滤的 SourceChunk 检索；
- 在权限过滤之后增加 BM25、向量召回和模型重排；
- 概念解释使用受证据约束的结构化模型输出；
- 将回答拆成 claims，并为每个 claim 独立绑定 citation IDs；
- 对 claim 与证据执行独立支持性检查；
- 为公式、图表和视觉页保留受审核 provenance；
- 收紧 archive lifecycle 状态门禁；
- 支持“检索—观察—补充检索或追问”的多步流程。

## 7. 练习选择与答案反馈

相关实现：

- `app/learning/service.py`
- `app/retrieval/practice.py`

### 7.1 练习选择不是自适应选择

当前系统识别题型、排除消息中已经出现的 practice ID，然后选择剩余候选中的第一道。模型没有参与理解：

- 用户希望训练的能力；
- 难度要求；
- 可用时间；
- 希望概念、推导、调试还是迁移；
- 当前对话中已经暴露的困难；
- 用户想循序渐进还是直接挑战。

### 7.2 当前练习依赖文本中的 practice ID

系统通过消息里是否出现 practice ID 判断题目是否已展示，并要求反馈请求再次携带 ID。用户自然回答“我的答案是……”时，系统不能稳健绑定上一题。

### 7.3 答案提取依赖字符串删除

`_extract_answer()` 会从用户文本中删除 practice ID、课程身份和提示词。若这些内容属于答案本身，可能破坏回答。多个课程、多个题目或多个代码块时风险更高。

### 7.4 反馈是单轮输出，不是持续辅导策略

模型一次性输出正确点、一个修正、下一层提示和页码，但不能显式：

- 先询问用户的推理过程；
- 根据回答选择提示层级；
- 区分概念误解、计算错误和表达不完整；
- 处理用户追问；
- 判断题目本身是否存在歧义；
- 根据新回答逐步缩小问题。

### 7.5 隐藏控制最小化（2026-08-21 已修复反馈输入）

练习反馈模型现在只接收题面、作答要求、当前答案，以及通过权限/身份/审核/哈希
校验的最小 SourceChunk 证据；不再接收 `expected_evidence`、evaluation 或 rubric。输出仍执行
结构、citation allowlist 和隐藏字段扫描。练习展示 rewrite 的历史输入边界应继续单独审计。

### 7.6 完整答案防护仍依赖关键词

用户可以不使用“完整答案”“标准答案”等固定表达，却要求等价的 submit-ready 解答。模型输出的 `next_hint` 也缺少独立的信息量和学术诚信检查。

### 7.7 改进方向

- 使用 confirmed 目标、用户显式难度和本轮题型历史进行确定性排序；
- 使用客户端状态或服务端签名但不持久化的练习上下文 token；
- token 至少绑定 active practice ID、shown IDs、course/version/unit 和 hint level；
- 不保存答案、分数、正确率或掌握度；
- 自然语言答案先由模型解析成明确的 `practice_id + current_answer`；
- 在线反馈只读取最小化的反馈依据投影，不直接暴露完整 evaluation；
- 对反馈结果增加完整答案和隐藏控制泄漏审查；
- 反馈绑定具体 SourceChunk，而不只绑定页码；
- 保持离线、逐题、来源锚定的独立语义审计，不使用硬编码判题器代替。

## 8. 多语言静态代码辅导

相关实现：

- `app/agent/context.py`
- `app/code_tutor/languages.py`
- `app/code_tutor/static_analysis.py`
- `app/code_tutor/service.py`

### 8.1 确定性事实主要局限于语法

Tree-sitter 主要报告 error/missing 节点；Python AST 只额外检查少量模式。当前确定性层无法系统提供：

- 类型错误；
- 控制流和数据流错误；
- 未定义符号；
- 资源生命周期问题；
- tensor shape 问题；
- CUDA 内存和同步问题；
- 并发竞争；
- 语言和工具链专用诊断。

模型可以提出语义假设，但缺少充分、可验证的静态事实。

### 8.2 缺少迭代式诊断循环

当前模型一次性返回 observation、hypotheses、next checks 和 next attempt。它不能显式执行：

```text
建立假设
  → 请求一个高信息量补充信息
  → 根据用户回答排除假设
  → 定位下一步
```

缺少输入、期望输出或首条工具链错误时，同时返回多个泛化建议不一定是最有效的辅导方式。

### 8.3 课程概念和引用选择依赖少量硬编码别名

代码中的 backward、grad、attention、softmax、shape 等别名只能覆盖少数 ML 概念，无法扩展到系统、算法、数据库、编译或其他课程。

### 8.4 非法引用会被静默过滤

模型若返回不属于 `allowed_citations` 的 ID，当前代码会过滤这些 ID，而不是拒绝整个模型 draft。这样可能保留一个已经违反引用合同的回答。

### 8.5 多轮代码版本可能错配

代码、错误和问题分别从最近消息中提取。用户先后提交两个文件、两版代码或多个错误输出时，系统缺少明确的 CodeArtifact 身份，可能把不同版本组合到同一次分析中。

### 8.6 缺少语言和代码位置约束

Prompt 要求模型按照正确语言分析，但输出合同没有要求每个诊断假设绑定语言规则、代码位置或语法节点，因此难以验证模型是否真的针对当前语言和当前代码。

### 8.7 学术诚信识别依赖关键词

只有同时匹配作业语境和完整解答词汇时才触发显式阻断。隐含的代写请求、分阶段拼接完整解答和伪装成普通代码请求的作业任务仍可能绕过简单规则。

### 8.8 改进方向

- 增加不执行代码的类型、控制流、数据流和语言专用静态分析；
- 为 clang/gcc/nvcc/rustc/Go/Java/LaTeX 等错误建立结构化解析器；
- 让模型一次只提出少量可区分的诊断假设；
- 缺少证据时优先提出一个高信息量问题；
- 使用受控语义检索选择课程概念和引用；
- 任何非法 citation ID 都应使 draft 失败并透明降级；
- 为本轮代码块建立非持久化 artifact ID、文件名和内容摘要；
- 要求模型诊断绑定真实代码范围、语言规则和验证步骤；
- 对模型输出增加学术诚信审查；
- 保持静态分析和 `ran_code=false`，不得在现有路径中调用编译器或解释器执行用户代码。

## 9. 建议整改优先级

### P0：影响任务正确性或数据正确性

1. 修复过期 inferred 画像可能被全量确认的问题；
2. 拆分目录课程身份和 online-ready StudyKit 身份；
3. 将普通自然语言的主路由改为完整对话上的结构化任务理解；
4. 保留确定性安全命令，但避免宽泛关键词提前截断模型；
5. 为多步骤请求建立 TaskPlan 和统一前置条件执行器；
6. 非法模型引用必须使整个 draft 失败，不得静默过滤。

### P1：影响材料学习和练习质量

1. 建立权限过滤的 SourceChunk 检索；
2. 增加受控语义召回、重排和 claim 级引用；
3. 将概念解释改为受证据约束的模型教学组织；
4. 为练习建立非持久化、签名的上下文绑定；
5. 最小化在线反馈模型可见的内部评价信息；
6. 支持逐层提示和多轮练习反馈。

### P2：提升个性化与专业诊断

1. 逐条确认、纠正和拒绝画像候选；
2. 增加背景熟练度、时间和证据类型；
3. 增加课程先修、难度、工作量、语言和学习成果；
4. 分开呈现用户适配度和在线 readiness；
5. 扩充代码静态分析和工具链错误解析；
6. 为代码诊断增加 artifact、语言规则和代码位置绑定。

## 10. 建议验收标准

整改后至少应满足以下验收条件：

### 意图与任务执行

- 多轮指代请求能够使用完整对话恢复当前任务；
- 一个请求可以显式拆成两个及以上受控子任务；
- 缺少课程、讲次、practice ID 或代码时只提出必要的澄清问题；
- 模型不能绕过课程身份、权限和 online-ready 门禁；
- 普通聊天仍不能触发 StudyKit authoring。

### 学习画像

- confirmed 事实必须具有有效原文证据和语义支持；
- 用户可以逐条确认、修改、拒绝和删除候选；
- 过期 inferred 事实不能被确认或用于正式建议；
- 不从代码、traceback、课程材料或模型推理中建立正式画像。

### 课程与材料

- 目录课程可以被导航，即使它没有 online-ready StudyKit；
- 材料问答只能检索当前用户有权访问的 MaterialSet；
- 每个课程事实都能追踪到 approved StudyKit 或允许的 SourceChunk；
- 回答中的主要主张分别绑定合法证据；
- 证据不足时能够澄清或透明拒绝，而不是补充外部课程事实。

### 练习

- 当前练习无需用户手工重复 ID 也能在本轮上下文中可靠绑定；
- 不持久化答案、分数、正确率或掌握度；
- 反馈不泄漏 expected evidence、evaluation 或完整标准答案；
- 模型失败时继续降级为原题提示、作答要求和允许页码；
- 离线独立逐题审计仍是练习内容质量门禁。

### 代码辅导

- 不标注语言的代码不会默认使用 Python；
- 所有路径继续返回 `ran_code=false`；
- 模型诊断绑定当前代码版本、语言和真实代码范围；
- 非法课程引用使模型结果失败并降级；
- 作业代写请求只提供诊断、验证步骤和分层提示；
- 不执行、编译或测试用户代码。

## 11. 推荐目标架构

```text
可信身份与会话
  → 完整对话任务理解
  → 结构化 TaskPlan
  → 能力前置条件与权限检查
  → 课程目录 / approved StudyKit / permission-filtered SourceChunk / 静态分析
  → 受约束模型推理
  → Schema、引用、隐私与学术诚信检查
  → 学习者可见回答
  → 根据结果继续执行、追问或透明降级
```

该架构让模型负责语义理解、任务分解和受证据约束的教学组织，同时继续由确定性代码掌握身份、权限、课程事实、审核门禁、数据持久化和安全边界。
